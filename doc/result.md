### 🚨 根因第三版（前两版都错，含编排者一版）· 假绿的真正机制
- **状态**：done
- **真因（编排者原样复现）**：
  ```
  F="frontend/src/data/gua-readings.ts frontend/src/data/liuyao-topics.ts"
  grep -o "必须" $F 2>/dev/null | wc -l   → 0     ← 报告「0 命中」= 绿
  grep -o "必须" $F                        → ugrep: No such file or directory
  grep -o "必须" 文件1 文件2 | wc -l        → 10    ← 真值

  ```
- **机制**：zsh **不**对未加引号的参数展开做单词分割（与 bash/sh 不同）→ `$F` 整串被当成**一个文件名** → 文件不存在 → 报错走 stderr → **被 `2>/dev/null` 吞掉** → stdout 为空 → `wc -l` 得 0。
- **三版根因的演进**：
  1. dev-content 初版「`grep -o` 对中文漏报」→ 证伪，编码正常
  2. **编排者二版「`-c` 数行 / `-o` 数次，中文放大了差异」→ 也错**：行数差只会少 1，变不成 0
  3. 三版（复现验证）→ 上述 shell 机制
- **编排者的方法论失误**：我用一条**相似**的命令（单文件）去测，而不是**原样重跑**出问题的那条（两文件 + 未加引号变量 + 吞 stderr），于是测的是别的东西 —— **这正是我上一轮教训 dev-content 时说的同一个毛病。**
- **已写入 PRD §16 的规则五**：**扫描脚本里永远不要写 `2>/dev/null`** —— 红线扫描的失败必须吵闹，吞掉 stderr 等于把「命令根本没跑成」伪装成「一个问题都没有」。
- **✅ 本项目的实际验收结论未受影响**：编排者与 test-agent 的扫描全部使用 node `fs.readFileSync` 逐文件读（**读不到会抛错，不会静默给 0**）。用正确形式重扫确认：

